# @starter/web

## Why this exists

The product: React Router v7 app + Hono API on a single Cloudflare Worker.

## Architecture

- `worker.ts` — Worker entry: `withSentry(sentryOptions, handle(build, app, { getLoadContext }))`; the `./build/server` import is generated by `pnpm build` and carries a `@ts-expect-error`
- `server/index.ts` — Hono app: `observabilityMiddleware` (logger + request id) → `securityMiddleware` (headers, CSP nonce, `no-store`) → origin redirect → `authMiddleware` (validates env, then db + auth per request) → Better Auth at `/api/auth/**` → `principalMiddleware` on `/api/v1/*` → versioned API at `/api/v1` → `app.onError(observabilityErrorHandler)`. **The order is load-bearing at three points**: observability first so it sees everything; security headers above the origin redirect so redirects carry them; the redirect above `authMiddleware` so auth never constructs on the marketing origin
- `server/security-headers.ts` — exports `securityMiddleware` as an **ordered list**; mount it with `app.use(...securityMiddleware)` and do not reorder at the call site. Hono unwinds post-`next()` code in reverse, so the immutable-response normaliser is registered last to run first. Reordering drops the headers silently while every isolated unit test still passes (`docs/security-audit.md` #5, #14)
- `server/api.ts` — `OpenAPIHono` routes; every route declares a zod schema (that's where the OpenAPI spec comes from). **Default deny**: every method+path outside `PUBLIC_OPERATIONS` (`GET /health`, `GET /doc`) requires a principal, so a new route is authenticated unless you say otherwise. CSRF is a same-origin check on every unsafe method, applied to session callers only — not `hono/csrf`, which is a no-op on `application/json` (#15). `/me` needs a principal; `/tokens*` needs an interactive session
- `principalMiddleware` is mounted on `/api/v1/*` only, so Better Auth's own routes keep owning their credentials
- `server/origins.ts` — optional split-origin topology. No-op unless `MARKETING_URL` is set; then app paths on the marketing host 302 to the app origin, and `/` on the app origin 302s back. Mounted **before** `authMiddleware`, so auth never constructs on the marketing origin. Adding a product route means adding its prefix to `APP_PATH_PREFIXES` (`docs/domains.md`)
- `load-context.ts` — passes `db`, `auth`, `logger`, `requestId` and `cspNonce` into React Router loaders (`context.db` / `context.auth` / …). The nonce is read by `entry.server.tsx` and handed to **`ServerRouter`**, which is the default for every nonce-aware component — `root.tsx` passes none of its own
- `app/entry.server.tsx` — `handleError` reports loader/action failures; the stream `onError` reports SSR render failures (Sentry dedupes the overlap). Expected 4xx `ErrorResponse`s — the router's own 404s for unmatched URLs, `data()` throws below 500 — are logged at `warn` and never reach Sentry, mirroring `observabilityErrorHandler`; deny-path tests in `app/__tests__/entry-server.test.ts`
- `app/routes.ts` — explicit route config (NOT file-based routing)
- `app/routes/_examples/` — reference pages, not registered as routes

## Rules

- New page: add to `routes.ts` → create route file → `npx react-router typegen`
- **Any link crossing the marketing/app boundary needs `<Link reloadDocument>`.** A plain `<Link>` navigates client-side, so `server/origins.ts` never sees it — in split-origin mode the app page renders on the marketing host and its auth POST takes a 302 that downgrades to GET. Applies to landing → `/login` `/register`, and login/register → `/`. Links staying on one side must NOT use it (`docs/domains.md`)
- New API route: add to `server/api.ts` with OpenAPI schema → `pnpm api:spec` → add matching MCP tool in `apps/mcp`
- **Auth guard: call `requireUser(context, request)` (`app/lib/require-user.ts`) in every protected loader, including children of the dashboard layout.** The layout loader is not a security boundary in React Router v7 — children run in parallel with it and a `.data` request can fetch one directly, so the parent's redirect never applies. Guard even a loader that returns nothing: it is the template the next page gets copied from (audit #10)
- **Sign-up does not sign anyone in.** `requireEmailVerification` withholds the session until the link is followed, so `/register` swaps the form for `VerificationNotice` and `/login` shows the same notice on `EMAIL_NOT_VERIFIED`. Never word that notice as "account created" — Better Auth returns the same shape for an existing address on purpose (ADR 003)
- **Anything minting a verification link passes `POST_VERIFICATION_REDIRECT` (`app/lib/auth-client.ts`) as `callbackURL`.** Better Auth defaults it to `/`, and `/verify-email` redirects there after auto sign-in — so omitting it lands a just-verified user on the landing page, which `server/origins.ts` then bounces to the marketing host while the cookie stays on the app host. It reads as "verified, then logged out". No e2e covers this leg (the link only reaches the dev server log), so the shared constant is the guard
- **The hero's shader background degrades or it crashes the landing page.** `app/components/landing/hero-background.tsx` mounts `MeshGradient` from `@paper-design/shaders-react` (pinned exactly — the package is pre-1.0). Three things are load-bearing: it renders only after `supportsWebGl2` says yes, because the library **throws from its constructor** on a null `webgl2` context; the CSS gradient underneath is unconditional, so the server render and every browser without WebGL2 still get a composition; and `prefers-reduced-motion` pins `speed` to 0, which the library does not handle itself. Colours for the fallback come from CSS (`bg-white dark:bg-black`), never from `resolvedMode` — the theme resolves client-side, so a JS-driven colour renders white on the server and black on the client. Playwright's headless Chromium has no WebGL2, so CI runs the fallback path on every e2e run (`tests/e2e/hero-background.spec.ts`)
- Secrets: never in `wrangler.jsonc` — `.dev.vars` locally, `wrangler secret put` in production
- Deploy only via `pnpm deploy:web` (runs the verify gate)

## Testing

- `server/__tests__/` — Hono routes tested directly via `apiApp.request()`, no Worker runtime needed
- **Coverage target: `server/` 90%+** — every API route gets a unit test asserting status, shape, and the version/spec contract
- Routes/loaders/UI have no unit target — they're covered by `tests/e2e/` (auth flow, health, spec); keep e2e locators role-based (`getByRole`), not `text=` (strict-mode ambiguity burned us before)
- **Stop any running dev server before `pnpm test:e2e`.** Playwright reuses a server on 5173, but e2e global-setup runs `db:reset` — a pre-existing server keeps a handle to the dropped D1 file and all auth calls fail with `SQLITE_CANTOPEN`. Same reason the `webServer` block uses `port:` and not `url:` — `url:` makes Playwright boot the server _before_ global-setup, so `db:reset` pulls the D1 file out from under it every run
- **`await waitForHydration(locator)` (`tests/e2e/helpers.ts`) before filling a form.** SSR markup is visible, enabled and editable a few hundred ms before React attaches to it, so Playwright happily fills an inert input — React then replaces the node ("element was detached from the DOM") or resets the controlled value and the form submits empty
- The `warmup` project loads every route once before the suite so Vite's route compile and dep pre-bundling — which ends in a full page reload — happen while nothing is asserting. Add new routes to `ROUTES` in `tests/e2e/warmup.setup.ts`
